# Индексация

Статус: реализована часть требований.

| Сделано | Ещё нет |
| --- | --- |
| команда `index`, регистрация и клонирование репозиториев | удаление и просмотр индексов, обновление только изменённых файлов |
| Java: классы, методы, вложенность | Kotlin, TypeScript, JavaScript, Python, VBScript, BPMN |
| PL/Plus: классы и операции ЦФТ, функции, запросы, вызовы | PL/Plus: раскрытие макросов, SQL из `execute immediate` |
| Groovy: сгенерирован парсер | Groovy: извлечение символов и запросов |
| SQL из строк Java-кода с восстановлением и полным разбором | файлы `.sql`; вызовы, наследование и импорты между символами |
| native SQL (включая `@Query(nativeQuery = true)`) | Spring Data, Hibernate, JPA; эмбеддинги |

## Что индексируется

- Репозитории, 200–300 штук. Каждый репозиторий — отдельный индекс в общем хранилище.
- Репозиторий задаётся либо локальным каталогом, либо URL — тогда CLI клонирует его сам (см. «Репозитории»).
- Языки и форматы:

  | Что | Чем разбирается |
  | --- | --- |
  | Kotlin, Java, TypeScript, JavaScript, Python | tree-sitter |
  | Groovy, PL/Plus (язык ЦФТ), VBScript | ANTLR, Python-рантайм |
  | BPMN (XML из Camunda и Sber PL Flow) | `xml.etree` из стандартной библиотеки |
  | SQL | `sqlglot`, диалект PostgreSQL |

## Репозитории

- Репозиторий регистрируется под именем. Для URL имя извлекается при клонировании — последний сегмент пути без `.git`; для локального каталога — имя каталога. Имя уникально: регистрация второго репозитория с тем же именем отклоняется.
- Клонирование идёт обычным `git` от имени текущего пользователя, с его ключами и настройками. Своих учётных данных CLI не хранит и не запрашивает.
- Клон кладётся в отдельный каталог `~/.code-crawler/repos/<имя>` и остаётся там после индексации — следующие обновления индекса работают с ним же.
- При каждой индексации в индексе фиксируются хеш коммита и ветка, по которым он построен.
- Локальный каталог должен быть рабочей копией git. Индексируются только файлы под контролем git; символические ссылки пропускаются.
- Повторная индексация заменяет индекс репозитория целиком, в одной транзакции: до её завершения сервер видит прежний индекс. Для клона перед этим выполняется `git pull --ff-only`.
- Файл, на котором разбор упал, пропускается с предупреждением; остальные индексируются.

## Парсеры ANTLR

- Грамматики лежат в `grammars/<язык>/`. Сейчас есть PL/Plus и Groovy; грамматики VBScript пока нет.
- Лексеры и парсеры генерируются из них под Python и коммитятся: `src/code_crawler/plplus/`, `src/code_crawler/groovy/`. Сгенерированные файлы руками не правятся и исключены из `ruff`.
- Изменил грамматику — перегенерируй и закоммить результат в том же изменении.
- В рантайме используется только Python-рантайм ANTLR (`antlr4-python3-runtime`); Java нужна лишь для генерации. Версия генератора должна совпадать с версией рантайма — сейчас 4.13.2.

Генерация (нужны Java и `antlr4-4.13.2-complete.jar` с Maven Central):

```bash
ANTLR="java -jar /path/to/antlr4-4.13.2-complete.jar -Dlanguage=Python3 -visitor -no-listener"

(cd grammars/plplus && $ANTLR -o ../../src/code_crawler/plplus PlpLexer.g4 PlpParser.g4)
(cd grammars/groovy && $ANTLR -o ../../src/code_crawler/groovy GroovyLexer.g4 GroovyParser.g4)
rm src/code_crawler/{plplus,groovy}/*.interp src/code_crawler/{plplus,groovy}/*.tokens
```

### PL/Plus

Что извлекается из файлов `.plp`:

- **Класс ЦФТ и его операция** — из пути файла: `…/<класс>/methods/<операция>/src/<секция>.plp` и `…/<класс>/criteria/<представление>/src/condition.plp`. Все секции (`public`, `private`, `execute`, `validate`) принадлежат одной операции.
- **Функции и процедуры**, объявленные в файле, включая вложенные.
- **Запросы к классам**: `select`, `locate`, `insert`, `update`, `delete`. Для каждого — классы-источники с видом доступа и реквизиты `псевдоним.[РЕКВИЗИТ]` с ролью (`select`, `where`, `write`, `order`, `group`, `having`).
- **Вызовы операций и функций других классов**: `::[КЛАСС].[ОПЕРАЦИЯ](…)`, `::[КЛАСС].[БИБЛИОТЕКА].функция(…)`, `[КЛАСС]::[ОПЕРАЦИЯ]…`.
- **Вызовы функций по короткому имени** внутри того же файла или той же операции (например, из `execute.plp` в функцию из `private.plp`).
- **Запись реквизитов своего объекта**: присваивание `[РЕКВИЗИТ] := …` в коде операции.

Стандартные операции ЦФТ считаются записью в таблицу своего класса независимо от содержимого: `NEW_AUTO` — вставка, `EDIT_AUTO` — изменение, `DELETE_AUTO` — удаление. Другие конструкторы и деструкторы без метаданных ЦФТ распознать нельзя: их запись реквизитов помечается как изменение.

Класс и реквизит переводятся в таблицу и колонку по соглашению ЦФТ: класс `PRC_RATES` — таблица `z#prc_rates`, реквизит `[CREDIT]` — колонка `c_credit`. Когда появятся метаданные из JSON, соответствие должно браться из них.

Ограничения:

- макросы не раскрываются: вызов или запрос, спрятанный в макросе (`&SelectDocs …`, `&LIB.proc(…)`), в индекс не попадает;
- вызов связывается с узлом, только если цель есть в том же репозитории;
- вставка в коллекцию (`объект.[РЕКВИЗИТ]%insert(…)`) не учитывается.

Запросы PL/Plus — не SQL, а собственный синтаксис ЦФТ над классами и атрибутами (`select x(x.[A]) in ::[CLASS] where …`). Они извлекаются из дерева разбора этой грамматики, а не через `sqlglot`; настоящий SQL встречается только в строках `execute immediate`.

Проверка на реальном репозитории (6351 файл `.plp`, 622 тыс. строк), без раскрытия макросов, разбор в два прохода (SLL, при ошибках — LL):

- 6334 файла (99,7 %) разобраны без ошибок, все — уже в SLL; ошибок лексера нет;
- скорость — около 6600 строк в секунду на ядро, самый большой файл (7 тыс. строк) — 1,4 с;
- 17 файлов с ошибками: 14 — макрос раскрывается в незавершённую конструкцию (открывает цикл, начинает запрос, подставляет ветки `case`), и по одному — блок чистого PL/SQL (`for rec in (select d.extract(...) …)`), ключевое слово `exceptionloop` в `insert … for i in a..b exceptionloop` и макрос с параметрами вида `(a:b, c:d)`.

Файл с ошибками всё равно даёт дерево: парсер восстанавливается и разбирает остальное.

### Groovy

Грамматика — официальная грамматика Apache Groovy с действиями и предикатами на Python. Она опирается на два базовых класса, написанных вручную (перенос логики Apache Groovy на Python) и лежащих рядом со сгенерированным кодом:

- `GroovyLexerBase.py` — учёт скобок (переводы строк внутри `( )` и `[ ]` игнорируются), различение деления и строки-регулярки `/…/`, границы GString;
- `GroovyParserBase.py` — семантические предикаты: объявление метода, объявление локальной переменной, вызов с аргументами или замыканием.

Лексер не бросает исключений на некорректном коде: ошибки остаются обычными синтаксическими ошибками парсера, и файл всё равно разбирается.

Скорость Python-рантайма сильно зависит от режима предсказания. На файле в 1000 строк: режим по умолчанию (LL) — около 125 строк/с, режим SLL — около 2000 строк/с. Поэтому разбирать нужно в два прохода: сначала в SLL, и только если он дал синтаксические ошибки — повторно в LL.

## Извлечение SQL

Весь SQL, встречающийся в репозитории, попадает в индекс. Диалект — PostgreSQL.

Из каждого запроса извлекается всё:

- таблицы и колонки;
- тип операции (чтение, вставка, обновление, удаление, DDL);
- условия (`WHERE`, `HAVING`);
- соединения и их условия;
- происхождение колонок: из каких колонок каких таблиц получена каждая колонка результата.

Запрос, собранный в коде по частям, восстанавливается в цельный текст перед разбором. Учитываются:

- конкатенация строк (`+`, `+=`, шаблонные и многострочные строки);
- `StringBuilder` / `StringBuffer` (`append`);
- `String.join`, `String.format`, `concat` и аналоги в остальных языках;
- константы и переменные, значения которых известны статически.

Фрагмент, значение которого статически неизвестно (параметр метода, результат вызова), заменяется заполнителем `__unknown__`; запрос разбирается дальше и помечается как восстановленный частично (`partial`).

Как учитываются ветвления:

- часть запроса, добавленная под условием или в цикле (`if (f) sb.append(...)`), включается в текст, а запрос помечается `partial`;
- если переменной в разных ветках присваиваются разные запросы, каждый попадает в индекс отдельно; то же для обеих частей тернарного оператора.

Что считается SQL: строка, которая после восстановления начинается как оператор SQL (`select … from`, `insert into`, `update … set`, `delete from`, `with … as (`, `merge into`, DDL). Если разобрать её не удалось, запрос всё равно попадает в индекс с `parsed = false`.

JPQL и HQL (`@Query` без `nativeQuery = true`, `@NamedQuery`, `createQuery`) как SQL не разбираются — это часть анализа Spring Data, Hibernate и JPA.

Ограничения текущей реализации:

- константы подставляются только из того же файла; константа из другого класса даёт `__unknown__`;
- без схемы БД колонку без префикса таблицы можно отнести к таблице, только если таблица в операторе одна; иначе колонка попадает в `unresolved_columns`.

SQL внутри PL/Plus уже адаптирован под PostgreSQL и разбирается тем же диалектом.

## Слой доступа к данным

Анализируется отдельно от общего разбора кода. Результат — связи «символ кода → запрос → таблица/колонка» с типом операции. Таблицы и колонки — это [слой данных](data-model.md), а не узлы графа.

- **Native SQL** — строки запросов в коде (JDBC, `JdbcTemplate`, `@Query(nativeQuery = true)`), файлы `.sql`, SQL внутри PL/Plus.
- **Spring Data** — интерфейсы репозиториев, запросы из имён методов (`findByStatusAndOwner`), `@Query` с JPQL.
- **Hibernate** — HQL, Criteria, маппинги `hbm.xml`.
- **JPA** — маппинг сущностей на таблицы (`@Entity`, `@Table`, `@Column`, связи), именованные запросы.

## BPMN

Индексируется структура процесса и её связи с кодом: делегаты, скрипты, вызовы сервисов и другие ссылки из элементов процесса на символы кода.

## Граф

Граф кода хранится в трёх таблицах (миграция `0001_graph.sql`): `repos` — зарегистрированные репозитории с веткой, коммитом и временем индексации; `nodes` — узлы; `edges` — рёбра. Структура БД в граф не входит — это отдельный [слой данных](data-model.md).

Узлы (`nodes.kind`):

| Вид | Что это | `qualified_name` |
| --- | --- | --- |
| `file` | файл исходного кода | путь от корня репозитория |
| `class` | класс, интерфейс, enum, record, аннотация (`attrs.type`) | `пакет.Внешний.Вложенный` |
| `method` | метод или конструктор | `пакет.Класс.метод` |
| `function` | функция или процедура PL/Plus | `КЛАСС.ОПЕРАЦИЯ.ФУНКЦИЯ` |
| `sql_query` | запрос, найденный в коде | `путь:строка` |

У `sql_query` в `attrs`: `text`, `operation` (`select`, `insert`, `update`, `delete`, `merge`, `ddl`), `partial`, `parsed`, `conditions`, `joins` (`type`, `table`, `on`), `lineage` (колонка результата → исходные `таблица.колонка`), `unresolved_columns`.

Рёбра (`edges.kind`):

| Вид | От → к | `attrs` |
| --- | --- | --- |
| `contains` | файл → класс, класс → класс/метод | — |
| `executes` | класс, метод, функция или файл → запрос | `line` |
| `calls` | функция или файл → операция или функция (PL/Plus) | `line` |

Для PL/Plus `class` — класс ЦФТ (`attrs.type = cft_class`), `method` — его операция или представление (`attrs.type`: `operation`, `criteria`); цепочка вложенности: класс → операция → файл секции → функция. У запросов PL/Plus `attrs.language = plplus`.

Запрос из поля класса (константа) привязан к классу; метод, который эту константу использует, получает своё ребро `executes`.

Какие таблицы и колонки запрос читает и пишет, записано ссылками в `data_refs` — см. [data-model.md](data-model.md).

## Регрессионная база перед UCM

Change `openspec/changes/baseline-regression-tests/` и тесты
`tests/test_baseline_regressions.py` фиксируют восемь исходных случаев:
неиспользованный SQL, конфликт констант между классами, перегрузки, quoted SQL
identifiers, синтаксическую ошибку, dirty worktree, одинаковый basename и
динамический SQL.

Известные дефекты legacy-поведения: SQL construction получает `executes` без
подтверждённого execution sink;
перегрузки имеют одинаковый qualified_name; quoted имена таблиц приводятся к
нижнему регистру. Parser diagnostics Java реализованы — см.
[java-diagnostics.md](java-diagnostics.md).
Dirty worktree читается с диска при сохранении прежнего HEAD, поэтому commit hash
сам по себе не описывает точное содержимое индекса. Basename остаётся уникальным
именем регистрации.

Тесты с `legacy` проверяют наблюдаемые ошибки, а не нормативную семантику будущего
UCM. При исправлении ошибки соответствующий тест обновляется вместе с кодом и
документацией. PostgreSQL integration coverage вводится отдельным change.

## Инкрементальные UCM snapshots

UCM API поддерживает fingerprints tracked-файлов, Git diff, invalidation зависимых
файлов и перенос facts неизменённых файлов в новый snapshot. Контракт analyzer,
ownership manifests и границы описаны в [ucm-incremental.md](ucm-incremental.md).
Текущая команда `index` по-прежнему использует legacy writer и полную индексацию;
управляемый переход чтения и миграция доступны через команды из
[ucm-legacy-migration.md](ucm-legacy-migration.md).


## Java parser diagnostics

Java file nodes сохраняют hash/byte_length фактически прочитанных bytes,
parse_coverage и structured diagnostics ERROR/missing/invalid UTF-8. CLI выводит
точные byte coordinates. Файл с восстановленным AST сохраняется как PARTIAL;
нестабильный при чтении файл пропускается с явной ошибкой. Подробнее:
[java-diagnostics.md](java-diagnostics.md).


## Нормативные Java symbols

Adapter `java_symbols` извлекает signatures/overload identity, parameters,
scopes и lexical occurrences в UCM через incremental API. Неоднозначные вызовы
не превращаются в подтверждённые CALLS. Legacy CLI/SQL extraction остаются
прежними. Контракт и ограничения: [java-symbols.md](java-symbols.md).

## Локальный Java Call Graph

`java_calls.index_java` строит UCM snapshot с проверяемыми declared-method CALLS,
ambiguous/partial candidates и ExternalReferences. Resolver использует каталог
только одного репозитория. Политика conversions, catalog invalidation и ограничения
описаны в [java-calls.md](java-calls.md). Нормативный snapshot пока не заменяет
полный legacy CLI и не утверждает выполнение найденного SQL.

## Java SQL construction

Opt-in `java_sql.index_java_sql` расширяет Java call graph SQL-конструкциями,
вариантами и происхождением fragments. Исправлено разрешение Java final field
constants по lexical type scope. Native SQL discovery не создаёт EXECUTES_SQL;
JPQL исключается. API, ограничения recovery и partial описаны в
[sql-construction.md](sql-construction.md). Legacy CLI writer сохраняется.

## Java SQL execution sites

`java_execution.index_java_execution` добавляет к constructions распознаваемые
JDBC/Spring sinks и локальные prepared origins. Preparation без execute не
создаёт execution; unknown origins сохраняются unresolved. API opt-in, legacy
writer сохраняется. Профиль и ограничения: [sql-execution.md](sql-execution.md).

## SQL semantic accesses

Opt-in `java_semantic.index_java_semantic(conn, repository_id, root, dialect="postgres")`
добавляет отдельные SQL statements, typed table/column accesses и links от execution
sites. Допустимы postgres/mysql/tsql; profile включает dialect и SQLGlot version.
Legacy SQL projection сохраняется. Partial/dynamic SQL не создаёт угаданных access
facts. Подробнее: [sql-semantics.md](sql-semantics.md).

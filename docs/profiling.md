# Профилирование CLI

Встроенный сэмплирующий профилировщик показывает, на что уходит время команды
`code-crawler`. Он работает внутри процесса, поэтому не требует прав
администратора и внешних инструментов, и видит рабочие потоки
(`asyncio.to_thread`), в которых идёт анализ.

## Включение

```bash
uv run code-crawler --profile index.prof index ~/work/billing
```

`--profile ФАЙЛ` — общий параметр, ставится перед командой и работает с любой
из них. Без него профилировщик не запускается и на работу не влияет.

## Как считается

Отдельный поток снимает стеки всех потоков процесса — раз в 10 мс, а пока идёт
вычисление на Python, реже (примерно 50 раз в секунду), потому что ждёт GIL:

- простаивающие потоки (ожидание задачи, события или сокета) пропускаются;
- если в момент замера не работает ни один поток, записывается стек главного
  потока с пометкой `[ожидание]` — так видно время ожидания ответа БД и
  внешних процессов (`git`);
- время кода на C (tree-sitter, pydantic, asyncpg) относится к вызвавшей его
  Python-функции.

Это статистическая оценка по настенному времени: доли надёжны для длинных
операций, для команд короче нескольких секунд замеров слишком мало. Замер
делается в момент, когда работающий поток отдаёт GIL, поэтому короткие функции
могут быть немного недо- или переоценены. Накладные расходы на анализе Java —
около 3 % времени.

## Результат

По завершении команды (и при успехе, и при сбое) в консоль печатается сводка по
функциям `code_crawler`: «всего» — доля замеров, где функция была в стеке,
«сама» — где она была на вершине. В сводке 25 функций с наибольшим «всего».

В файл пишутся все стеки в формате collapsed stacks — строка
`корень;…;вершина число_замеров`, кадр имеет вид `каталог/файл.py:функция`.
Формат читают speedscope и flamegraph.pl. В файле только имена функций и файлов
Python, исходников и данных индексируемого репозитория в нём нет.

Профилируется только процесс CLI. MCP-сервер этим механизмом не охвачен.

# Code review — code-crawler (2026-11-15)

**Baseline:** main @ `b5b3f35ee50fcb0d8546af57898a0436ae642415` (2026-11-15 16:30 UTC). **Previous audit:** `18ebcf7`. This is a static review of GitHub source, docs, SQL migrations and tests; no independent local benchmark was run. GitHub Actions [PG15 CI](https://github.com/resokk/code-crawler/actions/runs/43735828147) passed on baseline.

## Confirmed progress

- Core: immutable repository UCM snapshots, canonical CLI, typed read/validation/publication, source archives; Java/Groovy/PLPlus, SQL construction and execution, ORM, SQL lineage.
- Additional adapters: D01/D02 BPMN+Java bindings, D05/D06 OpenAPI 3.x + Spring/Feign, D07 Kafka, D10 Kotlin, D11 JavaScript/TypeScript and D12 VBScript; support remains explicitly PARTIAL where framework/compiler/runtime semantics are not available.
- Search: C01 persisted search documents/generations, C02 exact discovery, C03 latest/pinned/deployment contexts, C04 candidate resolution, C05 derivative cache and C06 bounded cross-repository traversal. These steps **do not** prove runtime invocation solely from declaration identity.
- A01 GC safety: explicit `jobs._SNAPSHOT_TABLES` allowlist and preflight avoid deleting third-party public tables merely because they have a snapshot_id column.
- Large-snapshot functionality: [docs/ucm-ingestion.md](ucm-ingestion.md) records PG15.20, 3,002 Java files, 1,060,524 entities, 405.4s indexing/staging/FK and 213.2s sliced validation, peak 1,012 MiB RSS. This removes the previous blocker “cannot ingest ~1M facts”; do not claim that it is fast enough for production without an SLO.
- Sliced validation uses ~170 MiB vs 688 MiB for full restoration on a 141,424-entity fixture but takes ~17.8s vs 4.8s. It still collects all SQL facts and key sets, so memory is not fully bounded.
- [PG15 query benchmark](query-indexes.md) on the 1,060,524-entity fixture reports symbol simple-name API ~10.31ms, most other tested structural API calls ~0.33–6.23ms. Synthetic workload and one host; not general P95.

## Verified problems and limitations, prioritized

### P0-Security — MCP still lacks merged repository ACL on current main

[docs/server.md](server.md) explicitly states no authentication or repository ACL; `server.py` performs searches in publication scopes. PR [#8](https://github.com/resokk/code-crawler/pull/8) implements A02 bearer authentication, repository grants, evidence checks, auditing and tests, but **is open at this baseline**. Until reviewed and merged, do not expose HTTP MCP to untrusted clients. A trusted server-wide `DISCOVERY_REPOSITORY_KEYS` is not per-principal authorization. Validate A02 with concurrent principals, denied evidence and migration-free startup fail-closed tests, then deploy audit log collection.

### P0/P1-Operations — main branch policy does not satisfy full A05 acceptance

[openspec/changes/a05-required-main-ci-check/evidence.md](../openspec/changes/a05-required-main-ci-check/evidence.md) records classic protection for non-admins with strict required `PostgreSQL 15`, but administrators can bypass; required PR/no-bypass policy and negative merge tests remain open. This is an administrative policy gap, not a failed CI run.

### P1-Performance — snapshot GC is the largest measured database bottleneck

[docs/ingest-jobs.md](ingest-jobs.md) and [docs/query-indexes.md](query-indexes.md) show GC of 141,424 entities ~120.9–124.0s versus batch-copy ~24.8–25.7s. Deferred FK work on deletion is the main cost. Temporary indexes on 19 snapshot FK columns reduced two GC trials to ~61–65s but are not yet a measured production design. No GC test for >1M facts; B06 is the next database optimization, not reimplementing A01's safety allowlist.

### P1-Semantic — SQL reader/writer search is name-based, not physical database-scoped

`search._accesses` (src/code_crawler/search.py, approximately lines 388–455) filters `ucm_sql_access_names` by normalized table/column/schema, not resolved `DATABASE_OBJECT` with database_key and version_key. Same-named tables in different connections can be grouped. Quoted and unquoted identifier spelling is also a source of ambiguity. Implement A03 explicit SYNTACTIC_NAME vs RESOLVED_DATABASE_OBJECT search, then A04 standardized execution-vs-candidate certainty.

### P1-Memory/latency — validation and search projection still hydrate too much data

`publication._validate_stream` avoids whole-snapshot Python models, but `check_semantics` requires all SQL facts, and key sets accumulate; the current 1M benchmark succeeds but SQL-dense repositories need their own scaling tests. `search_storage.rebuild_search_documents` calls `load_snapshot_batch` then builds `_records`, which can reintroduce full-snapshot RAM pressure. Complete B02 and add an isolated search-document streaming follow-up.

### P1-Operations — long-running transaction includes CPU analysis

`incremental.index_incremental` opens a transaction before analyzing each selected file slice and holds it through staging, cloning, archive and manifests (approximately lines 580–663 in prior reviewed implementation). B03 should separate capture/analyze from commit-critical writing while maintaining worktree verification, atomicity, snapshot/candidate correctness and CAS.

### P1-Discovery — new producer types are not yet visible to exact global lookup

`discovery._SUPPORTED` still marks `KAFKA_TOPIC` and `BPMN_WORKER` UNSUPPORTED even after D07 and D02 analyzers were added. Producers/definitions must be identified conservatively; a consumer subscription, external worker selector or name-only match does NOT prove a definition. Add separate bounded C10/C11 changes.

### P1-Security — source/evidence redaction policy unfinished

Source archives are intended for exact Evidence. Derived documents and future embeddings require explicit redaction policy, ACL and non-exfiltration constraints. A06 remains open; C07 must not run on raw private secrets.

### P2/Feature — missing adapter types and GraphRAG

D03/D04 reference-data JSON + loader lineage, D08/D09 GraphQL schema + Java resolver bindings, C07 vector/model registry, C08 hybrid ranking, C09 global MCP impact tools are still open. Kotlin/JS/TS/VBScript v1 profiles are useful but partial; full compiler/framework semantics are not claimed.

## Validation and uncertainty

- GitHub Actions PG15 on baseline: success; independent source/test execution was not performed for this review.
- PR #8 branch has its own CI and implementation; not counted as already deployed in main.
- No claim of a deterministic “worst-case P95” based on synthetic benchmark medians.
- Version selection, candidate identity and source Evidence can prove identity but not runtime call execution or deployment.
- Some legacy docs/roadmap checkboxes are stale after merges: [development-plan-v3.md](development-plan-v3.md) is the corrected prioritized status.

## Immediate recommendations

1. Review/merge A02 and enforce A05; keep HTTP server private until done.
2. B06: investigate GC FK index/trigger plans under PG15; protect source blobs and pinned snapshots.
3. A03/A04: make SQL answers unambiguous about database identity and execution certainty.
4. B02 and B03: reduce residual memory scaling and transaction duration; add streaming search projection as focused follow-up.
5. C10/C11: expose verified Kafka/BPMN declaration identities through discovery; avoid false positives.
6. Complete C07→C08→C09 and D03→D04 / D08→D09; add E01–E03 operational controls.

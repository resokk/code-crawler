## Риски и замечания

### P1 — новый риск: изменение истории миграций и неявное разрешение SQL schema

**Факты:** в коммитах между `b5b3f35` и текущим `main` переписаны миграции `0003`–`0029`: старые файлы содержали `public.ucm_*`, новые используют неквалифицированные имена. Это не обязательно приводит к сбою на PostgreSQL с обычным `search_path`, но **ранее развёрнутые БД не получают повторного применения этих файлов**.

`src/code_crawler/db.py:19-60` упорядочивает миграции по имени и хранит лишь `schema_migrations(name, applied_at)`, без исходного SHA/checksum; потому `db status` не выявляет изменение уже применённого SQL. `connect()`/migration runner не фиксируют `search_path`; поведение новых миграций и unqualified runtime SQL зависит от конфигурации PostgreSQL role/session. Два разных файла имеют prefix `0030_`: это допустимо при name-based ordering, но требует теста upgrade-order в уже эксплуатируемой БД.

**Риск:** разные миграционные истории могут показывать одинаковый «schema up to date», а custom `search_path` способен выбрать другую схему. **Не утверждается**, что существующие БД сломаны: нужен отдельный regression upgrade из фактической старой базы, а не только fresh init. Рекомендация: OpenSpec A07 — immutable-history/hash guard, явно принятая политика schema resolution и сценарии upgrade/role/search_path.

Референсы: [db.py](https://github.com/resokk/code-crawler/blob/e133cccb65a39fa62615cc484441a6f523ec6973/src/code_crawler/db.py#L19-L60), [old 0003](https://github.com/resokk/code-crawler/blob/b5b3f35/src/code_crawler/migrations/0003_ucm_repository_snapshots.sql), [new 0003](https://github.com/resokk/code-crawler/blob/e133ccc/src/code_crawler/migrations/0003_ucm_repository_snapshots.sql), [migration docs](db.md).

### P1 — GC и disk budget остаются измеренными узкими местами (B06/E02)

Безопасный A01 allowlist уже есть. Но [docs/ingest-jobs.md](ingest-jobs.md) фиксирует примерно 121–124с удаления 141424 facts (vs ~25с copy). В более позднем [B01](performance-baseline.md) все 3 GC попытки превысили **120с timeout** и откатились, не испортив published pointer. Причина — дорогие deferred FK checks; большая часть commit. На новом хосте попытки 1000-file clone и 3002-file index остановлены из-за нехватки места для PGDATA/WAL, не OOM. Требуются B06 + E02, реальный ресурсный бюджет и контроль свободного диска.

### P1 — Search Documents строятся с полной материализацией snapshot (C12)

`src/code_crawler/search_storage.py:169-240`: `rebuild_search_documents()` вызывает `load_snapshot_batch()`, затем материализует список `_records()`; это повторно создаёт память O(N) после исправлений B02. Требуется stream projection с atomic generation swap, parity hash/document IDs и fault injection.

### P1 — B05 ещё не достиг строгого сквозного resource budget

B03 уже выводит CPU анализ за пределы write transaction, а индексатор пишет spool и staged batches. При этом `_prepare_spool()` и source capture держат bounded-by-file/slice ресурсы, а фактический spool ~64MB на 400 файлов. Нет проверенного лимита по entity bytes/total temporary disk на arbitrary большие источники; в сочетании с disk-guard failures B01 это эксплуатационный риск. B05 активен, отдельные load/timeout/oversized-file tests нужны.

### P1 — Требуется штатный downgrade/upgrade regression для migration compatibility

Текущий CI подтвердил fresh migration chain, но не переход старой populated БД через изменение migration text и `search_path`. A07 покрывает обе проблемы; не исправлять задним числом исторические файлы снова. 

### P1/P2 — Governance (A05)

A05 остаётся открытым: код/README указывает required check PostgreSQL 15, но в [A05 evidence](../openspec/changes/a05-required-main-ci-check/evidence.md) admin bypass/no required PR ещё не закрыты; API защиты сейчас недоступен интеграции (HTTP 403 ранее). Следует проверить административным токеном и негативными PR-тестами. Green CI на SHA не доказывает защищённые правила merge.

### P2 — Неполное покрытие Discovery и глобальных MCP-инструментов

`src/code_crawler/discovery.py` всё ещё маркирует KAFKA_TOPIC и BPMN_WORKER как UNSUPPORTED, хотя D07 и D02 создают соответствующие статические producer/handler facts. C10/C11 должны проецировать только **достоверные декларации**, а не имена подписок или чужих targets. C09 добавит удобные global/impact MCP operations; текущие C02-C06 уже достаточны для bounded query-time identity path, но не runtime execution.

### P2 — GraphRAG и оставшиеся адаптеры

Активны C07 embeddings+pgvector, C08 hybrid retrieval, C09 MCP global, D03/D04 reference datasets/loader, D08/D09 GraphQL, E02 retention, E03 backup/restore, B07/B08 mixed/100+ repositories. Не создавать заново Java/Groovy/PLPlus/OpenAPI/BPMN и прочие уже реализованные адаптеры. Частичное покрытие Kotlin/JS/TS/VBScript, Kafka и Java SQL path cap отражать в запросах и Coverage.
